# Companion repository to live coding demo during the Paul Meehl Graduate School Meta-Research Symposium
Talk given on October 9th, 2026. Presentation can be found [here](https://tinyurl/PMGScnsodano)

The "Actions" tab shows examples of how scientists may want to use github actions to demonstrate that their analysis code is free of any seed hacking or order hacking.

Order hacking is the equivalent of seed hacking where the seed is set beforehand, e.g. 42, but the data order is not. Models that are highly dependent on data order can be 'seed hacked' without changing the seed from preregistration. If data is collected 1. by the same people performing the analysis and 2. after the code is preregistered then it is hard to prove that e.g. the order of rows in the published csv is not the precise order that makes their order-dependent model perform the best. Examples of models that are dependent on data order: anything that uses stochastic ("mini batch") gradient descent where the dataset is not trained on all at once (which would remove order effects) but instead in small batches. 

# 01: Naive seed hacking
This action builds a R container and runs `rmarkdown::render("01_naive_seed_hacking/seed_hack.Rmd")`. The result is a reproducible output that is seed hacked, that is, a hyper specific seed is set **in the body of the code file** that produces a result which is an extremely rare outlier from the process being studied. In this case, it is a series of 50 coin flips where there are 40 heads. Another way of looking at it is that it's a series of 10 coin flips with 8 heads, 'replicated' 5 times. The coin flips are a parallel to some process being modeled by a scientist that has some element of randomness within it (random weight initialization, dropout, etc)

# 02: Order hacking
The difference between this and the first example is that I am now downloading from an osf project where I posted a `.csv` file. Open data is considered by many to be a open science trust indicator, but I did not document the process of generating that data file; as a result, I can shuffle the row order of the data until it matches with the seed I preregistered that I'd use ("42") in this example. The result is that on a binary classification task ("is this penguin from the palmer penguins dataset MALE or FEMALE?") my 'model' (flipping a coin, saying "MALE" if heads, "FEMALE" if tails) performs at 97.5% accuracy over 333 instances, when the expected accuracy is roughly 50% (data has balanced classes). This is an example of why merely preregistering code before data collection with a pre-committed-to seed of 42, or 0, is not enough to ensure there isn't seed hacking going on. 

# 03: Environment hacking
This is a demo of one possible form of more sophisticated seed hacking that a highly motivated adversary may be interested in doing. The example I give in my presentation is someone 'poisoning' compiled code in common library like `dplyr` by changing a C++ function like `dyplr_extract_chunks` that is called in the common R function `dplyr::mutate` to change the global seed to whatever they choose, in this case '42' (because as I showed in the order hacking example, this seed matched with the order of the 'dubious_penguins.csv' dataset produces a highly unrealistic result). I also show a very naive way you may make your results seem 'robust' by replicating with multiple 'different seeds' but in reality all you are doing is setting the same seed multiple times. For this to work, you may decide to change the model slightly so that it gets some data points wrong on purpose just to make things seem less suspicious. Thus over 5 'different' seeds, my coin flip model predicts the sex of the penguins with >95% accuracy. 

However, I as of yet do not know enough about R/C++ to write this up myself, so instead I've given a dummy example of 'shimming' the `set.seed` function to always set the seed to 42. However you can't see this in the .Rmd code because I used an R flag so that this shimming step happens when the 'pipeline' is run. Still, in my github action this is transparent as the code I called is written out in public: 
**.github/workflows/environment_hack.yml**
```{yml}
        run: Rscript -e 'set.seed <- function(s){base::set.seed(42)};set.seed(42);rmarkdown::render("03_environment_hacking/environment_hack.Rmd")'
```

This is one of the main benefits of the actions-based workflow for reproducing results: the command run on the command line to generate the results is visible to anyone auditing. 

One last thing about environments: To make sure that poisoned code is not used, it is imperative that the renv environment specifies where to download the packages from and to use rebuild=TRUE in the renv::restore() call so that even if the git repository has the local cache checked in to github, renv will not install from the local, potentially poisoned, cache. If you want maximum auditability, the hash of the installed package should also be recorded, allowing you to track any deviations of the installed packages from what the pinned version's hash is (as reported by the package repository you are installing from) 


# 04: No hacking
Using `beacr`, there is no 'set' seed that gets registered prior to either data collection, data posting, or analysis; it is only *generated* at runtime. Moreover, unlike using system native random generation methods or other dynamic seeding methods (e.g. writing `set.seed(Sys.time())` in your code), when re-running the action the GitHub actions runner will **not** generate a new seed, but rather read from the seed log generated by `beacr`. This makes it possible to completely reproduce an analysis by running the action fresh again--the entire pipeline reruns, from installing the operating system, all of the system libraries needed to compile the R packages used in the project, installing those packages at the specific pinned versions defined in the renv.lock file (**from** a transparent, ideally auditable public package repository e.g. CRAN), and running the pipeline with no suspicious command line flags that might affect the environment. 

It is possible to make a Action reproducible without `beacr` by defining a function that, for example, first checks for a 'seed.txt' file and if it doesn't find one then call `Sys.time()`, save it to the .txt, and in the future use that for every run. However, `beacr` validates the logged seed with a third party source of truth rather than with a file that is saved in the repository (and which can be potentially tampered with by the code running from that repository). It also allows for other features such as connecting a preregistration to the seed (making the seed not just unknowable prior to running, but inseparable from your preregistration). This is maybe not so important if you think about preregistrations as documents meant to be published prior to running analyses (when the timestamp of the prereg publication should serve to prove it was written before running the analysis), but it allows for interesting future opportunities to **prove that an analytical result dependent on seed WAS preregistered and done so without prior knowledge of seed, WITHOUT posting publicly what the registration is**. For example, if people are very concerned about being 'scooped'.

How would you do this? Use the **hash** of the preregistration document along with the `beacr`-generated seed. Then, when the analysis is published, you can release at a future date your hypothesis and show that the hash of the file you released is equivalent to the hash used to generate the original result. The reason this would work is that we currently have hashing algorithms that are **collision resistant**, meaning that it is incredibly unlikely you can produce two files that hash to the same hash value, and if you do, it's incredibly unlikely that both of them would be intelligible hypotheses. In other words, *you can't just write two files with two different hypotheses and then release the one that matches your results*, because those two files will have two different hashes, and in practical terms it is computationally infeasible to tweak one of the files a bunch of times until you find one version where it looks mostly the same but has the right hash you're looking for.
